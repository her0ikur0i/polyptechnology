## Four deployment defects, found before a single token was spent

Every one of these was invisible to the test suite and appeared within minutes
of actually trying to run the service. This is the third time this project has
learned the same lesson, so it is recorded plainly.

**The secret file path was hard-coded to `/root/.config/polyp/provider-secrets.env`.**
The service runs as `polyp-factory` under `ProtectHome=true`. It could not read
that file and never could. Now `PROVIDER_SECRETS_FILE`, defaulting to the old
path so developer machines are unaffected, with the deployment pointing at
`/etc/polyp-ai-factory/provider-secrets.env` (`0640 root:polyp-factory`).

**`PROJECT_WORKSPACES_ROOT` defaulted outside `ReadWritePaths`.** Exactly the
class of bug CONTRACT-014 M10 found for attachments, in the sibling setting
nobody re-checked. Set explicitly in `sequence.env`.

**`Type=notify` with notifications from a child process.** Node cannot send a
unix datagram without a native module, so readiness goes through
`/usr/bin/systemd-notify` — a child. systemd's default `NotifyAccess=main`
rejected every ping with "reception only permitted for main PID", the unit never
became ready, and start timed out twice. Fixed with `NotifyAccess=all`, the
documented setting for exactly this case. The trade-off is recorded in the unit
itself rather than glossed: any process in the cgroup can now send
notifications, including the provider CLIs this service spawns.

**`MemoryDenyWriteExecute=true` is incompatible with this workload.** It forbids
the writable-executable mappings a V8 JIT needs. The workaround, `--jitless`,
also disables WebAssembly — and the supervisor died with
`ReferenceError: WebAssembly is not defined` **immediately after producing a
real reply**. Turned off, with the reasoning stated: this unit runs _our_ code,
while untrusted AI-authored code executes in the Docker sandbox
(`src/worker/planner.ts`) with `--read-only`, `--cap-drop=ALL`,
`--network=none`. Hardening the wrong process at the cost of the service running
at all is not a security win.

## Streaming, proven by observation rather than by test

The first drill showed **0 chunks** afterwards, which looked like a failure and
was not: the driver clears progress rows once the answer becomes a real message.
Querying after completion can only ever return nothing.

Re-run while polling _during_ the reply:

```
t+10s  chunks=0/0     state=running
t+12s  chunks=1/938   state=running     ← fragment visible mid-flight
t+14s  chunks=0/0     state=succeeded   ← cleared on success, by design
```

A row written by `polyp-sequence.service` and read by a separate `psql`
connection is direct evidence that fragments cross the process boundary, which
is the entire reason they are durable.

## A real gap that only the real run could reveal

That first fragment was **938 characters** — one blob, not a stream. The CLI's
`--output-format stream-json` emits complete assistant messages, so "streaming"
meant "the answer arrives before process teardown", not "watch it type". The
unit tests could never have caught this: they fed the adapter an event shape
this author invented.

Capturing real CLI output found `--include-partial-messages`, which emits the
provider's own SSE events:

```json
{
  "type": "stream_event",
  "event": {
    "type": "content_block_delta",
    "delta": { "type": "text_delta", "text": "1" }
  }
}
```

The adapter now reads those, and a subsequent drill showed a 9-character
fragment mid-flight instead of one 938-character blob at the end.

One trap came with it: **with partial messages enabled the CLI emits both the
deltas and a complete `assistant` message carrying the same text.** Emitting
both would double every answer. The adapter ignores the complete message once
any delta has been seen, and keeps it as the fallback for a CLI build without
partial support — both behaviours are now tested.
