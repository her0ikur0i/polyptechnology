## Testable scenarios for the owner to run by hand on staging

1. Open `http://127.0.0.1:4180/` (via the SSH tunnel) -- confirm the SPA
   loads and the Overview page shows real (empty, on this fresh staging DB)
   data rather than placeholder/mock content.
2. `/policy` -- create a draft policy using the dedicated envelope fields
   (not raw JSON), validate, approve, activate, then create a second draft
   and roll back to the first. Confirm each state transition is reflected
   immediately.
3. `/settings` -- confirm the Telegram panel shows "Configuration
   incomplete" and "Webhook route not registered" (both correct for this
   instance, since no bot token was supplied).
4. `/approvals` -- confirm the registry renders (empty on this fresh
   instance) with `decidedBy`/`decidedAt` columns present in the table
   header, ready to populate once a real decision occurs.
5. `/providers` -- confirm the "Fallback reason" column and "Rework
   history" panel render (the latter will show its empty state on this
   fresh staging DB, since no task has escalated across providers yet).
6. Create a project via `/factory-live` or the dashboard's project-creation
   flow, then trigger "Start code generation" -- confirm a task is queued
   (it will stay `queued`, since the background supervisor is not running
   on staging by design; this proves the request path, not full execution).
